Runner Forex 3D: Phase 3 Requirements
Client: Kevin
Deadline: 6 December 2026
Phase 3 covers: infinite worlds, enemies, collectible gems with gem revive, the Luxury Castle with its trading-chart challenge, the main menu with the Forex Quiz, and Firebase saving. Kevin's PDFs contain many more ideas (30 characters, shop, ads, leaderboard and more). Those are for Phase 4; see the last section. Where his documents disagree, this document follows his latest instructions.
Ground rules
* Work in the existing Unity repository from Phase 2. Keep the Cyberpunk, Labyrinth (Maze) and Space worlds, their environments and their portals. Extend them; do not rebuild them.
* Mobile game for Android and iOS, portrait orientation. Design reference is 1080 x 1920 (9:16), but the game must fill each phone's screen without stretching, cut-off gameplay or black bars. The runner, Abbot (the dog), lanes, obstacles and touch controls must stay in frame.
* Enemy and art designs must be original. Kevin does not want demons, aliens or pharaohs, and nothing copied from existing games.
* Any third-party asset, music or plugin must be licensed for commercial use in a monetized mobile game. Keep a list of every one with its source and license; it goes in the handover.
* Put tunable numbers (distances, gem costs, spawn rates, rewards, timers) in config assets such as ScriptableObjects, not hard-coded, so they can be balanced later.
* No server-side code in this phase. Firebase stays on the free Spark plan, which does not allow Cloud Functions. All checks are client-side.
Game loop
The game has no final level. The player runs forever and moves between worlds through portals, in this fixed order:
1. Cyberpunk City, then a portal to the Labyrinth (Maze).
2. Labyrinth, then a portal to Space.
3. Space, then a portal to the Luxury Castle.
4. Luxury Castle: run inside, sit at a computer and complete 5 trading challenges. On success the player earns 1,000 coins, stands up, and the portal to Cyberpunk City unlocks. The loop then starts again.
A portal appears after a configurable distance in each running world. Running continues after every portal and after the castle challenge; the challenge pauses the run but must not end it.
1. Infinite worlds
* Turn each existing world into an endless run built from reusable track segments that are spawned ahead of the player and recycled behind (object pooling). Memory use must stay flat no matter how long the run lasts.
* Difficulty increases gradually with distance (speed, obstacle density, enemy frequency).
* Every generated layout must be passable. No impossible combinations of obstacles and enemies.
* Show the distance run during gameplay and save the player's best distance.
* Cyberpunk City: reuse the existing city sections and obstacles; add moving obstacles and assemble segments in random order.
* Labyrinth: reuse the existing maze. Add branching paths, random but safe layouts and a guaranteed way through every section.
* Space: reuse the existing environment. Add moving platforms, gravity-themed obstacles and continuously generated safe routes.
* Coins and gems spawn along the track in every world (see section 3 for gems).
2. Enemies
Kevin calls the enemies "FOMO Bots". Each world gets its own variant, and the same bots also appear inside the castle.
* Cyberpunk: neon-style robot guard.
* Labyrinth: a guard or creature that roams the maze.
* Space: flying drones.
* Castle: FOMO Bots moving through the interior during the indoor run.
Requirements for all enemies:
* Clear silhouettes and a readable warning before an attack (wind-up animation, glow or sound), so the player can react.
* Enemies can come from in front, and from behind where that is still fair. The player avoids them with the normal swipe controls (lane change, jump, slide), and the player character uses its dodge animations.
* Fair collision boxes that match what the player sees.
* Enemy count and speed scale with the difficulty curve.
* Being hit ends the run and opens the revive screen (section 3).
3. Collectible gems and gem revive
* Gems are collectible pickups in every world, including the castle interior. They should be rarer than coins and clearly different from them.
* The gem balance is saved (section 7) and shown in the game UI.
* When the player loses a run, show a revive screen with the current gem balance and two choices: spend gems to revive, or end the run and restart for free.
* Revive cost and the maximum number of revives per run are configurable. Suggested starting values: 1 gem for the first revive, doubling each time, at most 3 revives per run.
* A revive puts the player back at a safe point, clears nearby obstacles and enemies, and gives a short period of invulnerability.
* Gems are deducted exactly once, and only after the revive succeeds. A retry or reconnect must never charge twice.
* No gem purchases or ad revives in this phase. Leave space in the revive screen for them later.
4. Luxury Castle
The fourth location, where the trading challenge happens. Kevin's concept image is "Mansion and Game Flow Concept.jpg" in this folder. Use it for the look of the castle; where it differs from this document (for example, it shows three exit portals), follow this document.
Exterior
* Large lit-up castle with grand gates, a red-carpet entrance, landscaped grounds and luxury sports cars parked outside.
* Two friendly security guards at the entrance, animated. As the player approaches, one guard lets them in and the giant doors open.
Interior run
* Luxury Baroque look: marble hall, chandeliers, gold details, elegant sofas and furniture, large framed trading-chart paintings, dramatic lighting.
* The player runs through the interior, avoids obstacles and FOMO Bots, and collects coins and gems. Kevin wants the castle coins to show the face of Abbot, his dog.
* A trading floor with many computers showing animated candlestick charts. Decorative computers can be instanced copies; only the one the player uses needs to be interactive.
* Castle music: a mysterious, luxury-feel track that is royalty-free or licensed for commercial use. Record the license.
Computer, reward and exit
* The player walks to a computer and sits down (sitting animation). A smooth camera transition moves to the computer screen. The player is safe from enemies while seated.
* Computer sounds (keyboard, interface beeps) play during the challenge, with the castle music underneath.
* After passing, play a reward effect for the 1,000 coins (coin burst and sound), then the stand-up animation, then a portal-unlock animation as the portal to Cyberpunk City opens. There is only one exit portal.
* Camera: third person while moving; a clear, readable view of the computer screen on a phone while seated.
5. Castle computer challenge
The castle has its own bank of 30 chart challenges (Appendix A). It is completely separate from the Forex Quiz in the main menu (section 6). Do not mix the two banks or reuse one for the other.
Challenge data
* Store the 30 challenges as editable data (JSON or ScriptableObjects), not in code. Each challenge has: number, level, currency pair, timeframe (H1 or M15), chart scenario, choices (BUY, SELL, WAIT), correct answer, explanation, and the candle and RSI data used to draw its chart.
* Challenges 1 to 10 are beginner, 11 to 20 intermediate and 21 to 30 advanced. Each visit still draws from all 30.
Chart screen
* An animated, fictional chart with green and red candles, a yellow liquidity-sweep line, support and resistance lines, an RSI(14, Close) panel with lines at 70 and 30, and a label with the pair and timeframe.
* The chart must match the scenario text. If the scenario says price sweeps below support and a bullish candle closes back above it, the chart must show exactly that. Draw each chart from its stored candle data and animate the last candles forming.
* Challenge 15 needs a candle that is still forming (not closed) when the question appears.
* Challenges 24 and 27 cannot be shown by the chart alone. Add an on-screen note: a "High-impact news soon, spreads widening" banner for 24, and a "Stop-loss risk too high for this account" label for 27.
* Three large buttons: BUY, SELL and WAIT. Show a progress indicator (for example "Challenge 2 of 5") and the countdown timer.
* After each answer, show whether it was correct, the correct answer and the explanation from Appendix A.
Rules
* Each visit draws 5 different challenges at random from the 30. Avoid repeating the previous visit's challenges where possible.
* All 5 correct: award exactly 1,000 coins once and save immediately, then play the reward, stand-up and portal-unlock sequence (section 4).
* Prevent duplicate reward claims through retries, reconnects or app restarts during the reward.
* Timer: 40 minutes maximum per attempt. It is a limit, not a waiting period.
Wrong answers and retries
* A wrong answer shows the explanation and fails the attempt, with no reward.
* The player can retry straight away with a fresh random set of 5. The 40-minute timer restarts with each attempt.
* If the timer runs out, the attempt fails the same way.
* After 3 failed attempts, a "Leave without reward" option appears and opens the portal, so the player is never stuck in the castle.
* Questions per visit, reward, timer length and the number of failed attempts before the leave option are all configurable.

* A practice round asks 5 random questions from the chosen level with no repeats in the round. Shuffle the order of the choices.
* After each answer, show correct or incorrect with the explanation. Show the score at the end of the round.
* Save the best score for each level to the player's profile (section 7). Practice rounds give no coins; keep a configurable coins-per-correct-answer value set to 0 in case Kevin wants it later.

7. Firebase save system
Kevin owns the existing Firebase project "ForexRunner". Cloud Firestore is created and Email/Password sign-in is enabled. Kevin has given access to adilshafiq784@gmail.com; please confirm you can open the project. Do not enable other sign-in methods or billing without asking.
Accounts
* Register both the Android and iOS apps in the Firebase project and add the Firebase Unity SDK (Authentication and Firestore).
* Screens: register, sign in, sign out and password reset (Firebase's reset email). The player stays signed in between launches.
* Delete account option in SETTINGS. Apple requires this for any app that lets users create an account.
* Never store passwords ourselves; Firebase Authentication handles them.
What is saved
* Coins, gems, best distance and scores, world progress, castle challenge history (completed sets and recently drawn challenge IDs), Forex Quiz best score per level, and settings.
* Characters, purchases, profile and inventory do not exist yet. Add empty fields for them in the player document now (selected character set to the starter) so Phase 4 can fill them in without changing the data structure.
* One Firestore document per player, keyed by their user ID, for example players/{uid}.
* Save automatically at sensible points: end of run, castle reward, revive, world change, quiz result, and app pause or quit. The player never has to save manually.
* Progress restores when the player signs in again after reinstalling, or on another phone, including Android to iOS and back.
* Offline play works using Firestore's offline cache and syncs when the connection returns. Handle interrupted saves without losing or duplicating coins or gems (use transactions or a "reward already granted" flag).
Security
* Firestore security rules: each signed-in player can read and write only their own document. Nothing is open to everyone.
* No Cloud Functions or server-side validation in this phase (Spark plan).
